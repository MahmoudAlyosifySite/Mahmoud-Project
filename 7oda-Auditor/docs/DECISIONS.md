# Decisions and deviations from the proposal

Each entry says what the proposal asked, what the MVP does, and why. Dates are 2026.

## D1. Pattern length (2026-11-24)
**Proposal:** a 1–1.5 s pattern with 6–10 taps (gaps 80–250 ms), 2–3 ramps of 150–300 ms, plus silences; at most 2 s per check.
**Problem:** those ranges add up to about 2–3.5 s, which breaks both the 1.5 s pattern and the 2 s check targets.
**MVP:** 6–8 taps with gaps of 80–150 ms, exactly 2 ramps of 150–250 ms (each followed by 80–120 ms of silence), and a 50–100 ms lead silence. Median pattern ≈ 1.45 s (range ≈ 1.0–1.9 s). The 0.25 s pre-roll before the pattern is the quiet window for tremor and grip angle, so no extra silence is inserted. The recorder runs continuously while a recording screen is open, so a check costs pattern + 0.25 s post-roll + processing.

## D2. v0 classifier (2026-11-24)
**Proposal:** RBF SVM, or LDA plus logistic regression.
**MVP:** a shared-covariance Gaussian model (the LDA decision rule without the projection step) on standardized features, with Ledoit–Wolf shrinkage (floor 0.1) and a Cholesky factor. Distances are Mahalanobis.
**Why:** closed form and deterministic (identical on the phone and in Python), retrains in milliseconds, works with a single enrolled person (LDA projection and SVMs do not), and gives a distance with a natural absolute threshold for "Unknown". The full-dimensional distance also rejects strangers who differ in directions the enrolled people do not span, which a K−1 dimensional LDA projection would throw away.

## D3. Prototypes per person, hand and accessory (2026-11-24)
Every `(person, hand, accessory)` is its own class. Name margins are measured only against other people; hand margins only against the same person's other hand. This is the proposal's "several prototypes per person" made concrete.

## D4. Hand head (2026-11-24)
**Proposal:** a hand head with right / left / two-handed outputs.
**MVP:** a pooled right-vs-left Gaussian model trained on everyone's samples. No two-handed class until there is data for it.

## D5. Calibration normalization (2026-11-24)
On one phone, subtracting the on-table response is a constant offset and does not change identification. It is kept because it makes features comparable across phones (cross-device test, v1 training).

## D6. Thresholds are defaults (2026-11-24)
`absFactor = 1.5`, `nameMargin = 6`, `handMargin = 3`, `minNCC = 0.30` and the quality thresholds are starting values. The Lab screen exposes them and the evaluation harness tunes them on held-out sessions, as the proposal requires.

## D7. Not in the MVP (2026-11-24)
- PIN fallback: replaced by labelled test runs in the Lab (the user states who is holding).
- v1 learned encoder on the phone: the training pipeline belongs in `research/` and ships only if it beats v0 on cross-session accuracy, as the proposal says.
- Jailbreak sensor injection: out of scope, as in the proposal.

## D8. Building and testing without a Mac (2026-11-24)
The development server is Linux and running a Swift toolchain there was not permitted, so all Swift code is compiled and tested on GitHub Actions: the core package on Linux and macOS, the app with `xcodebuild` on an iOS simulator and for a generic iOS device. The Xcode project is generated by `tools/gen_xcodeproj.py` (Xcode 16 format with synchronized folders), so no XcodeGen install is needed to open it.

## D9. What simulated results mean (2026-11-24)
The physics simulator validates the pipeline's mechanics (alignment, features, thresholds, sequential checks, Unknown). Its accuracy numbers are not evidence about real hands. Real accuracy comes only from the week-2 pilot and the 20-person study.
